rverilator.wasm — Verilog-2005 simulation in your browser

One engine, two CLI faces (ADR-0009): rverilator (vl-sim) and riverilog→rivvp (riv-elab + riv-kernel), both compiled to WebAssembly (~1.2MB). Expectations in corpus/ were recorded from real Verilator 5.050 — the engine running here reproduces them byte-exactly. Waveforms are parsed by the same shared vl-vcd reader the CLI and Bun use — one parser behind every tier.

riverilog face: sources compile to the RIV-1 design (0 bytes, the -o out.riv artifact), then rivvp interprets it — the same two-step contract as the native CLIs. The $finish banner is the iverilog-face form.

XLS-generated Verilog, verified independently — in this browser

Google XLS (DSLX → IR → Verilog HLS) ships a pluggable VerilogSimulator interface whose only built-in implementation is Icarus Verilog; Verilator appears upstream only as a doc example. The cards below take XLS-generated Verilog from this repo's oracle-recorded corpus and simulate it with rverilator-wasm — an independent, clean-room check that does not trust XLS's own high-level (DSLX/JIT) evaluation. stdout is compared byte-for-byte against the Verilator-recorded expectation. (XLS-generated code, Apache-2.0 — see corpus-external/xls/NOTICE.)

Spec verification: RTL ↔ golden-model lockstep, in this browser

The spec-verification layer (ADR-0007) checks an RTL against a three-layer machine-checkable spec: an executable golden model, per-cycle protocol invariants, and a lockstep harness — the same composition cargo test -p spec-i2c gates natively, here running wholly inside wasm. Detection power is the product: pick a surgically broken RTL variant and watch the spec catch it, named. The waveform is the run's VCD rendered as SVG (ADR-0005).
